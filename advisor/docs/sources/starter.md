## Обязательный минимум из кейса

1. Серверный каталог: банк, карта, категории, ставки, заданные ограничения и лимиты, даты действия условий. Обновление не создаёт дублей. Устаревшие данные не выдаются за актуальные.
2. Пользователь выбирает категорию и сумму. Backend воспроизводимо рассчитывает ожидаемый кэшбэк в рублях, возвращает топ-3 и полный список подходящих вариантов. Есть фильтрация по категориям, подробные условия и дата их актуальности.
3. «Мои карты»: пользователь добавляет карты из справочника и может сравнить только свои карты. Список хранится на сервере и доступен после перезагрузки. Здесь «добавить карту» значит сохранить ID записи каталога, а не привязать платёжный инструмент.
4. Эталонный сценарий: «Супермаркеты», 2 500 ₽ → топ-3 в рублях → полный список и условия → смена категории меняет результат → повтор того же запроса на неизменных данных даёт тот же результат. Должен работать расчёт в режиме «Мои карты».

Кейс допускает подготовленные данные; банковские API, реальные транзакции и платные внешние сервисы не нужны. Нельзя запрашивать номер карты, CVV, SMS-коды и другие платёжные секреты. Для прототипа можно использовать подготовленный серверный seed; вымышленные условия помечать как учебные. Мокать данные можно, подставлять заранее готовый топ-3 вместо расчёта нельзя. В PDF критериев: −20% за отсутствие деплоя (APK, если мобильная разработка) и −30% за невыполнение минимума кейса. Не считай автоматически, что PWA требует APK или заменяет APK — уточни трактовку у организаторов. Готовность деплоя проверь рано.

## Продуктовые решения, которые переносим

- Основная идея: **подсказать карту до оплаты за минимум действий**. Mobile-first интерфейс; PWA рассматриваем как формат, не как обязательное условие кейса. «Супермаркет», «Кафе», «АЗС» — быстрые категории. Пользователь добавляет свои карты один раз. Если без суммы точного победителя нет, не обещай его: предложи ввести сумму. Полный калькулятор «категория + сумма → топ-3 в рублях» остаётся обязательным.
- Показываем «почему эта карта первая»: ставка, применившийся лимит, сумма и дата условий. Пример учебных данных для 2 500 ₽: A — 10%, лимит 100 ₽ → 100 ₽; B — 6%, лимит 300 ₽ → 150 ₽; C — 4%, лимит 200 ₽ → 100 ₽. Побеждает B. Для равных результатов явно выбери стабильный порядок.
- Модель расчёта: деньги в целых копейках; единое документированное округление; детерминированное ранжирование. Предложи политику для пропущенной категории, просроченных условий и пересекающихся периодов. Заданный лимит учитываем в MVP; точный остаток месячного лимита по истории транзакций не обещаем.
- **Нет NFC-оплаты из PWA.** Пользователь платит внешним кошельком или физической картой. PWA не выбирает карту в кошельке автоматически и не видит реальных транзакций. Не проектируй обходы, хранение реквизитов, LLM в продукте или интеграции со Spirit: расчёт и объяснения формируются обычным кодом.
- **Опционально, после обязательного минимума:** «Записать покупку». Подставляем категорию, сумму если она известна и рекомендованную карту, позволяем выбрать фактически использованную. Один раз задаётся «обычная карта» для сравнения. В месячный отчёт включаем только явно записанные покупки; показываем расчётный кэшбэк и разницу относительно обычной карты, а не фактическое начисление. Сохраняем оба расчёта и версию условий на дату покупки, чтобы обновление каталога не меняло историю. Не смешивай эту статистику с аналитикой кликов и не суммируй прогнозы как реальные выплаты. Учёт использованного месячного лимита — отдельная допфича; если он не реализован, явно покажи пределы оценки.

## Приоритет реализации и проверки после MVP

- **P0 — сначала MVP:** ручной выбор категории, сумма, реальный серверный расчёт, условия карт, «Мои карты» и работающий деплой. Пока этот сценарий не проходит приёмку, не начинай интеграцию с банками, геолокацию и отчёт. Для P0 не нужны внешние сервисы.
- **P1 — подсказка категории:** после MVP проверь поиск по названию торговой точки на небольшом локальном справочнике брендов и их вариантов написания. При однозначном совпадении предложи категорию (например, «Супермаркет» или «Ресторан») с возможностью исправить одним тапом. Для неизвестного или неоднозначного названия оставь ручной выбор. Тип заведения — подсказка, не подтверждение MCC терминала и не гарантия кэшбэка. Геолокация и внешние карты не нужны на первом шаге.
- **P1 — переход в банк:** отдельно проверь идею кнопки «Открыть приложение банка» после рекомендации. Сбер и Альфа — кандидаты для проверки, не подтверждённые интеграции. Используй только официально подтверждённую ссылку, не угадывай схемы URL. Кнопка открывает подтверждённый экран по явному тапу; она не должна обещать запуск СберПэй/Альфа‑Пэй, выбор карты или проведение платежа, если это не подтверждено. Не передавай реквизиты и не считай открытие приложения оплатой. Сначала проверь один банк на реальном телефоне из браузера/установленной PWA: что открывается с установленным приложением, что происходит без него и доступен ли понятный запасной сценарий. Если подходящая ссылка не подтверждена — не показывай кнопку; оставь инструкцию «Откройте приложение банка вручную».

Не обещай максимум по рубрике: укажи, чем команда реально подтвердит инженерное качество и продуктовую пользу.
