# Контракт первой интеграции (проект v1)

## Данные и расчёт

Учебный каталог `training-v1`. Строки ниже — вход, а не готовый рейтинг. Банк и карта каждой строки: «Учебный банк {ID}», «Карта {ID}». Категории: supermarkets = Супермаркеты, cafe = Кафе, fuel = АЗС. Для детерминированных тестов дата 2026-11-20 UTC, дата актуальности 2026-11-01, период [2026-11-01, 2027-11-01), нижняя граница включена. В приложении — текущая серверная дата UTC; если стенд запускается вне периода, подготовьте новую явно датированную версию, не отключайте проверку.

| cardId | categoryId | rateBps (100 = 1%) | limitKopecks | minAmountKopecks |
|---|---|---:|---:|---:|
| A | supermarkets | 1000 | 10000 | 1 |
| B | supermarkets | 600 | 30000 | 1 |
| C | supermarkets | 400 | 20000 | 1 |
| D | supermarkets | 200 | 10000 | 1 |
| D | cafe | 800 | 30000 | 10000 |

Фильтровать по набору карт, периоду, категории и минимальной сумме. Нет действующего правила — исключить, не подставлять 0% или базовую ставку. Для целой положительной суммы в копейках: процент в копейках = `(amountKopecks * rateBps + 5000) // 10000`; возврат = минимум процента и лимита. `limitApplied` истинен, когда лимит уменьшил результат. Месячный лимит считаем доступным полностью; остаток неизвестен, сообщить об этом пользователю. Сортировка: возврат по убыванию, затем ASCII cardId по возрастанию. Каждая карта занимает одну позицию; из подходящих старых правил с совпадающими псевдонимами используется максимальный возврат. Топ — первые три позиции. Импорт принимает пару необязательных полей `bankName` и `cardName` с единым значением для карты на весь пакет. Импорт транзакционный: ключ правила (cardId, categoryId, validFrom), повтор — upsert; пересекающиеся периоды одной пары отклоняют весь пакет.

## HTTP (JSON)

`POST /api/recommendations`, тело: `{"categoryId":"supermarkets","amountKopecks":250000,"scope":"all"}`. `scope` = `all`, `mine` или `manual`. В последнем режиме `categoryId` содержит название ручной категории. `catalogVersion` относится только к общему справочнику и его названиям. Ответ 200: объект с `asOf` (ISO-дата), `catalogVersion`, `top3` и `allMatches` (массивы одинаково устроенных позиций). Пример одной позиции:

```json
{"cardId":"B","bankName":"Учебный банк B","cardName":"Карта B","categoryId":"supermarkets","cashbackKopecks":15000,"calculation":{"amountKopecks":250000,"beforeLimitsKopecks":15000,"afterCategoryLimitKopecks":15000},"rateBps":600,"limitKopecks":30000,"limitApplied":false,"minAmountKopecks":1,"validFrom":"2026-11-01","validUntilExclusive":"2027-11-01","updatedOn":"2026-11-01"}
```

При нулевой сумме: 422, `{"field":"amountKopecks","code":"positive_integer_required"}`. Пустая известная категория — 200 и два пустых массива. Неизвестная категория — 422 с полем categoryId. Ошибка сервера не равна пустому результату. Рубли форматирует UI, второй калькулятор на клиенте не нужен.

## Карты пользователя и покупки

`GET /api/cards?categoryId=…` — каталог с действующими условиями; `GET /api/cards/{id}` — подробности. `GET /api/me/cards` — сохранённые ID; `PUT`/`DELETE /api/me/cards/{id}` — идемпотентное добавление/удаление. При добавлении проверять существование карты. Привязка к непрозрачной cookie сессии (HttpOnly, SameSite, Secure на HTTPS); связи с картами в серверной БД, уникальность пары сессия+карта. Не принимать пользовательский ID из тела для выбора чужого списка. При пустом `mine` не переходить на `all`.

`PATCH /api/me/manual-cards/{id}/rate` принимает `{"categoryName":"Такси","rateBps":300}` и возвращает 204. Меняется ставка указанного правила. Период, остальные правила, идентификатор карты и начисления за месяц сохраняются. 404 означает отсутствие карты у текущего владельца или указанного правила, 409 — неоднозначное совпадение старых названий, 422 — недопустимую ставку или категорию.

При записи покупки через `POST /api/me/purchases` клиент может передать `Idempotency-Key` (16–128 ASCII букв, цифр, дефисов или подчёркиваний). Повтор с тем же ключом и данными возвращает исходный ID в рамках аккаунта, даже если покупку успели удалить. Тот же ключ с изменёнными данными возвращает 409. Для отдельной покупки нужен новый ключ.

В каждом результате `calculation` содержит сумму покупки, округлённый возврат по ставке до ограничений и возврат после лимита на покупку. Итоговый `cashbackKopecks` учитывает применимые личные месячные ограничения.

`GET /api/me/spending` возвращает для каждой покупки `cashbackComparison`: `usedCardCashbackKopecks`, `bestCardName`, `bestCashbackKopecks`, `differenceKopecks`. Сравнение использует сохранённые оценки по одной операции с лимитом на покупку. Месячный остаток не восстанавливается. `null` означает, что подходящей альтернативы или сохранённой оценки нет. Сохранённая нулевая оценка возвращается как `0` и отличается от отсутствия данных.



- `PUT /api/me/usual-card` с `{cardId}` задаёт карту для сравнения только из своего кошелька. Текущий выбор возвращается в `GET /api/meta` как `usualCardId`. `DELETE /api/me/usual-card` или совместимый `PUT` с `{"cardId":""}` снимает выбор. Удаление обычной карты из кошелька тоже снимает выбор, не меняя историю.
- `POST /api/me/purchases` принимает `{categoryId,amountKopecks,chosenCardId,requestId?}`. Проверяет категорию до записи, принадлежность карты и применимость её условий; запоминает оценки выбранной, лучшей и обычной карты на серверную дату. Ответ 201 — `{id,calculatedKopecks,recommendedKopecks}`. Повтор записи, сделанной до появления поля `id`, может вернуть прежний ответ без ID. ID можно получить из журнала. Не читает банковские операции и не подтверждает платёж.
- Для повтора используйте `Idempotency-Key`: 16–128 ASCII букв, цифр, `-` или `_`. Старый `requestId` в теле также принимается (непустая печатная строка до 128 символов после удаления крайних пробелов, допускаются короткие ключи). `requestId: null` не отменяет заголовок. При передаче обоих ключей они должны совпадать. Тот же ключ и данные в одном аккаунте возвращают первоначальный ответ без второй записи; изменённые данные — 409. Без ключа каждый запрос создаёт отдельную запись.
- `GET /api/me/stats`: `month`, `usualCardId`, `purchases`, `count`, `calculatedKopecks`, `recommendedKopecks`, `missedKopecks`, `usualKopecks`, `versusUsualKopecks`, `note`. По умолчанию — текущий календарный месяц UTC. Опциональный query `month=YYYY-MM` ограничивает выборку указанным месяцем текущего пользователя; неверный формат — 422. Если хотя бы для одной покупки нет оценки обычной карты или покупок нет, сравнение с обычной картой — `null`, а не ноль. `POST /api/me/stats/comment` запрашивает необязательное текстовое пояснение `{comment}`; Пояснение формируется на сервере из журнала без внешнего запроса.

## План нескольких покупок

`POST /api/me/purchase-plan` сравнивает от 2 до 8 покупок по картам текущего
кошелька. Поддерживает гостевую и авторизованную сессии. Категории принимает из
`/api/meta`, суммы задаются целыми копейками. План применяет правила, действующие
на дату расчёта, и остатки общих лимитов по картам и по категориям за текущий месяц UTC.

```json
{"purchases":[{"categoryId":"supermarkets","amountKopecks":100000},{"categoryId":"transport","amountKopecks":100000}]}
```

Ответ содержит `month`, `optimized`, `sequential`, `gainKopecks` и
`assumedFullCardIds`. В обоих вариантах возвращаются `totalKopecks` и массив
`purchases` в исходном порядке. Каждая строка содержит `cardId`, `cardName`,
`bankName` и `cashbackKopecks`. При отсутствии положительного возврата
поля карты равны `null`, сумма равна нулю.

`sequential` выбирает самый высокий возврат по очереди, уменьшая расчётный
остаток после каждой покупки. `optimized` максимизирует сумму за весь список.
При равных итогах возвращается тот же выбор, что и в `sequential`. Покупка
целиком относится к одной карте. При заданном лимите и неизвестных начислениях
расчёт предполагает полный остаток, а идентификатор карты указывается в
`assumedFullCardIds`. План не записывает покупки и не расходует сохранённый лимит.


### Объяснение результата плана

`explanation.code` принимает `same_total`, `shared_limit` или
`better_allocation`. `changes` содержит только изменившиеся покупки с
`purchaseIndex` (с нуля), строками `optimized` и `sequential` и разницей
`deltaKopecks`. Для `shared_limit` дополнительно возвращаются
`cardId`, `cardName`, `reserveFromPurchaseIndex`, `useAtPurchaseIndex`
и `savedBalanceKopecks` — сколько остатка сохранилось на этой карте к моменту
следующей указанной покупки. `assumedFullCards` добавляет имена карт к
`assumedFullCardIds`.

Например, в супермаркете и транспорте по 1 000 ₽ карта А даёт 10% с общим
остатком 100 ₽. Карта Б даёт 8% и 1% соответственно. Итог плана 180 ₽,
последовательного выбора 110 ₽. Код `shared_limit`, индексы 0 и 1, разницы
по покупкам −2 000 и +9 000 копеек.

## Настройка месячных лимитов

`GET /api/me/cards/{cardId}/cashback-limits` возвращает `month`, `card` и
`categories` для карты из текущего кошелька. У карты и каждой категории есть
`limitKopecks`, `usedKopecks` и расчётный `remainingKopecks`. В категориях
дополнительно есть `categoryId` и `label`. `card.bankBalanceApplied` показывает,
что остаток карты взят из сверки с банком.

`PUT` сохраняет лимит карты и перечисленные категории одной транзакцией.
Суммы задаются целыми копейками, `null` очищает поле. При смене месяца сервер
вернёт 409 для устаревшей формы. Лимиты сохраняются между месяцами, начисления
привязаны к указанному месяцу UTC.

```json
{"month":"2026-11","card":{"limitKopecks":300000,"usedKopecks":10000},"categories":[{"categoryId":"all","limitKopecks":100000,"usedKopecks":10000}]}
```

В личном расчёте применяется лимит на покупку, затем месячный остаток
по применённому правилу, затем месячный остаток по всей карте. Правило
`all` расходует один и тот же остаток для всех покупок, где оно применяется.
Если начисления оставлены пустыми, расчёт предполагает полный лимит.
Введение лимитов и просмотр расчёта не создают записи покупок в журнале.

## Сверка остатка по карте

1. `GET /api/me/stats` возвращает в каждой покупке `id`, `cardId` и
   `actualCashbackKopecks`. `null` означает, что пользователь ещё не внёс
   фактическое начисление. `PUT /api/me/purchases/{id}/cashback` принимает
   `{"amountKopecks":8000}` (204). Передача `null` удаляет отметку,
   а 0 подтверждает нулевое начисление.
2. `GET /api/me/cards/{cardId}/cashback-reconciliation` возвращает за текущий
   месяц UTC `month`, `cardId`, `reconciledAt` (ISO 8601), исходный
   `bankRemainingKopecks`, `deductedKopecks`, `remainingKopecks` и
   `accruals`. До первой сверки дата и суммы сверки равны `null`.
   В `accruals` только фактические начисления по покупкам этой карты за
   текущий месяц. Каждая строка содержит `purchaseId`, `cardId`, `date`,
   `categoryId`, `purchaseAmountKopecks`, `actualCashbackKopecks`
   и `includedInBankBalance`.
3. На тот же адрес отправляется `PUT` со всем набором отметок.
   Например, при начислениях 50 и 80 ₽ покупка 17 уже входит в остаток банка.

```json
{"month":"2026-11","bankRemainingKopecks":30000,"includedPurchaseIds":[17]}
```

Ответ 200 в формате GET. В примере `deductedKopecks` = 8000, а
`remainingKopecks` = 22000. Повтор с теми же данными сохраняет дату.
При новой сверке указываются новый остаток и все вошедшие в него начисления.
Подтверждённые начисления, которые ещё не учтены банком, вычитаются из
переданного остатка, минимум до нуля. Расчётные суммы из журнала не участвуют.
Сверенный остаток имеет приоритет над прежней ручной настройкой лимита на
этот месяц и используется в обычной рекомендации и плане покупок.
Для записей журнала используется месяц покупки. Валидный остаток 0 ₽
остаётся известным остатком. При смене месяца прежняя сверка не применяется.
Смена месяца или отметки недоступных начислений по своим покупкам дают 409,
например `{"message":"Список начислений изменился. Откройте сверку заново"}`.
После 409 загрузите список заново через GET и перепроверьте отметки перед PUT.
Функции сверки и фактических начислений требуют входа. Чужая или несуществующая
карта или покупка даёт 404, в том числе покупка, переданная в `includedPurchaseIds`.

## Месячная сводка кэшбэка

`GET /api/me/stats?month=YYYY-MM` подходит для виджета сводки. По умолчанию
используется текущий месяц UTC. Ранее возвращаемые поля и порядок карт сохранены.

| Поле | Значение |
|---|---|
| `count` | Покупки, записанные в КопиКэше за месяц. |
| `actualCashbackKopecks` | Сумма фактических начислений, внесённых пользователем. `null` при отсутствии подтверждений. |
| `actualCashbackCount` | Покупки с внесённым начислением, включая подтверждённые 0 ₽. |
| `calculatedKopecks` | Ожидаемый возврат по выбранным картам на момент записи покупок. |
| `missedKopecks` | Разница между сохранёнными оценками лучшей и выбранной карты по тем же покупкам. |
| `cards[]` | `cardId`, `name`, `count`, `spentKopecks`, `cashbackKopecks` (расчётный), `missedKopecks`, `actualCashbackKopecks` и `actualCashbackCount` для каждой выбранной карты. |

Редактирование или удаление подтверждённого начисления отражается при следующем
запросе. Начисление относится к месяцу покупки. Сверка банковского остатка
и изменения текущих ставок не пересчитывают сохранённые оценки.

### Редактирование категорий и отчёт

`PATCH /api/me/manual-cards/{card}/rate` обновляет одну строку текущего
кошелька. `categoryId` и `label` (или `null`) идентифицируют исходное
условие. `source: "base"` выбирает базовое правило, `source: "active"`
выбирает подключённые условия текущего месяца UTC. Старый запрос без
`source` сохраняет прежний выбор по `label`. `rateBps` обязателен,
`newLabel` меняет название в той же строке. Коллизия названия возвращает
409, неизвестная строка — 404. Ограничения и категория расчёта сохраняются.

`POST /api/me/stats/comment?month=YYYY-MM` возвращает разбор выбранного
месяца. При отсутствии модели разбор строится на сервере из статистики:
количество покупок, расчётная сумма и подтверждённые начисления.

Фронтенд отдаёт `/manifest.webmanifest` и `/sw.js`. Старые адреса
`/api/pwa/manifest.webmanifest` и `/api/pwa/sw.js` также разрешаются на
фронтенде для установленных PWA. Контейнер API запускает `backend:app`.
