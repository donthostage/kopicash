# Перенос «Советника» и автодеплой Spirit

Цель: `https://gitlab.t-education.com/hack-ovb-06/sdk`. Приложение находится в `advisor/`. Корневой пайплайн подключает общие шаблоны Spirit и `advisor/.gitlab-ci.yml`. Код и задачи приложения-примера удалены из рабочей версии, коммиты остались в истории. SQLite, `.env` и приватные ключи в Git не переносить.

`advisor:test` проверяет архив конкретного коммита и браузерные сценарии. При `ADVISOR_DEPLOY_ENABLED=1` после тестов на основной ветке собираются `advisor:build` и `advisor:build-frontend`, затем `advisor:deploy` обновляет оба контейнера в проекте `advisor-spirit`. Образы помечены `advisor-<SHA>` и `advisor-frontend-<SHA>`. Первый запуск можно сделать через **Run pipeline** на основной ветке. Устаревший SHA пропускается, merge requests не деплоятся.

`deploy/docker-compose.yml` описывает FastAPI, `deploy/docker-compose.frontend.yml` — Nginx со статическими файлами из `frontend/Dockerfile`. Деплой применяет оба файла одной командой Compose. Nginx обслуживает страницы и перенаправляет `/api/*` и `/healthz` на backend по внутренней сети. Только frontend привязан к `127.0.0.1:8766` на ВМ. Для внешнего адреса нужен действующий HTTPS-прокси на `443`, направленный на этот upstream. Правило ingress `8000–8100` не открывает `8766`; порт backend открывать не нужно.

Уже настроенные `SPIRIT_DOCKER_SA_KEY`, `DEPLOY_HOST`, `DEPLOY_USER` и `DEPLOY_KEY` используются повторно. Проверенный публичный ключ текущей ВМ хранится в `advisor/deploy/spirit-vm-ed25519.pub`; CI формирует из него временный `known_hosts` с адресом `DEPLOY_HOST`. При замене ВМ или ротации ключа обновите файл после проверки отпечатка через доверенную консоль. Отдельная переменная `DEPLOY_KNOWN_HOSTS` не нужна. На ВМ root должен иметь действующий доступ на чтение Spirit Registry — например, через уже настроенный `dp auth configure-docker`. Если доступ истёк, восстановите его по инструкции площадки до запуска. Включайте `ADVISOR_DEPLOY_ENABLED=1` только после подготовки ВМ.

## Первое переключение ВМ

1. Если «Советник» уже работал на ВМ, сделайте консистентную копию SQLite; не перезаписывайте `/var/lib/advisor` и `/etc/advisor.env`. На новой ВМ создайте каталог данных с отдельным непривилегированным владельцем и `/etc/advisor.env` (пустой файл допустим, режим `0600`). Внешний HTTPS-прокси должен выставлять `X-Forwarded-Proto`, а не копировать значение из клиентского запроса.
2. Если на ВМ есть старый `advisor-update.timer` и `advisor.service`, в согласованное окно отключите их автозапуск, остановите и дождитесь завершения `advisor-update.service`. Порт 8766 должен быть свободен. Не запускайте два процесса «Советника» на одной SQLite.
3. Включите переменную и запустите пайплайн основной ветки. Compose использует `/var/lib/advisor` и публикует `127.0.0.1:8766`. HTTPS-прокси настраивается отдельно: переключать публичный адрес на этот upstream только после проверки `/healthz` и SHA в GitLab. Внутренняя проверка включает контрольный расчёт. Если контейнер примера всё ещё запущен, после проверки его можно остановить отдельно; пайплайн его не трогает.

Readiness запуска проверяет через frontend и `/frontend-revision`, и `/healthz`, и контрольный расчёт. При сбое возвращаются предыдущие файлы Compose и локальные образы. Для первого перехода с backend-only поддерживается предыдущий `compose.yml`, а новый frontend останавливается, чтобы освободить порт. Сохраняйте файлы предыдущего релиза в `~/.advisor-releases/`. Без предыдущего контейнера неудачный запуск останавливается. Откат схемы БД — отдельная операция из резервной копии.
